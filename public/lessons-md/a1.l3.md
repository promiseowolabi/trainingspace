# A1.L3 — A Scalar Engine

_Track A1: Autograd from Scratch · ~20 min · trainingspace_

> An autograd engine is a number that remembers how it was made. Give every value a list of parents and a closure that knows its local derivative, walk the graph backwards once, and you have the core of PyTorch in about a hundred lines.
A1.L2 walked a graph by hand. To make a program walk it, every intermediate value needs to carry three things beyond its number:

1. **`grad`** — a slot for ∂L/∂(this value), starting at 0.
2. **`_prev`** — the values it was computed from: its edges in the graph.
3. **`_backward`** — a closure that, when called, pushes `self.grad` into its parents' `grad` using the local derivatives of the operation that made it.

The trick is that you never build the graph explicitly. Overload `+`, `*` and friends so that every operation creates a new value with those three fields filled in, and **running the forward pass records the graph as a side effect**. This is the design popularised by Andrej Karpathy's *micrograd*, and it is, in miniature, how PyTorch's autograd works.

---

```python
class Value:
    def __init__(self, data, _children=(), _op=""):
        self.data = float(data)
        self.grad = 0.0
        self._backward = lambda: None     # leaves have nothing to push
        self._prev = tuple(_children)
        self._op = _op

    def __mul__(self, other):
        other = other if isinstance(other, Value) else Value(other)
        out = Value(self.data * other.data, (self, other), "*")

        def _backward():                  # runs later, during the walk
            self.grad += other.data * out.grad
            other.grad += self.data * out.grad

        out._backward = _backward
        return out
```

---

Read the closure carefully, because every operation you write in lab 01 has the same three ingredients:

- **`out.grad`** is the upstream gradient — by the time this runs, every consumer of `out` has already added its share.
- **`other.data`** is the local derivative of `a·b` with respect to `a`. It is a *forward* value, captured by the closure — the stored activation of T0.L4.
- **`+=`** accumulates, so a value used twice gets both contributions.

Then `backward()` itself is three steps:

```python
def backward(self):
    order = topological_order(self)   # every node after all of its inputs
    self.grad = 1.0                   # dL/dL
    for node in reversed(order):      # consumers before producers
        node._backward()
```

---

> **[segfault]** **The overwrite.** Writing `self.grad = other.data * out.grad` passes every simple test — until a value is used twice. `y = x·x + x` at x = 3 should give 7; the overwrite gives 1 or 3 depending on visit order. Lab 01's `accumulates` check is exactly this expression.
> 
> **The recursion.** The obvious topological sort is a recursive depth-first search. Python's default recursion limit is 1,000 frames, and a training graph is thousands of nodes deep: one node per operation per layer per token. Lab 01's `deep-graph` check builds a 5,000-node chain. Use an explicit stack: push a node, push its children, emit the node when you come back to it.

## A neuron on top

Once `Value` exists, a neuron is ordinary Python — the engine does not know or care that it is part of a neural network:

```python
def neuron(weights, bias, xs):
    return sum((w * x for w, x in zip(weights, xs)), bias).tanh()
```

Stack neurons into layers and layers into an MLP, compute a loss, call `loss.backward()`, and every weight's `.grad` holds its partial derivative. Then the step from T0.L1 — and one easily forgotten line:

```python
for p in params:
    p.data -= lr * p.grad
    p.grad = 0.0            # gradients accumulate across backward() calls too
```

PyTorch has the same semantics, which is why every PyTorch loop calls `optimizer.zero_grad()`. Forgetting it is the same bug as the overwrite, inverted: gradients from step 1 leak into step 2.

---

- **337** — parameters (an MLP 2 → 16 → 16 → 1 with tanh, built from Value)
- **68,140** — graph nodes (one forward pass over 100 examples — every add, multiply and tanh is a Python object)
- **148 ms** — forward + backward (118 ms forward, 30 ms backward on the reference laptop)
- **0.4 MFLOP/s** — useful throughput (60,800 matmul FLOPs ÷ 148 ms — about 5 million times slower than numpy's matmul (T0.L3))

## Why this is not how you train a model

The engine is correct and hopeless. Each scalar multiply allocates a Python object, a tuple and a closure; the forward pass spends most of its 118 ms creating 68,140 of them. Useful arithmetic runs at 0.4 MFLOP/s — five million times below what a numpy matmul achieves on the same laptop.

The fix is not a faster scalar engine. It is to make each node hold an **array** and each operation a whole matmul, so that one graph node does a million FLOPs instead of one, and the per-node Python overhead disappears into the noise. Same graph, same walk, same `+=` — lab 02 builds it, and A1.L4 works out the local derivatives of array operations, which is where the new difficulty lives: shapes.

**Q1. Your engine passes every test except one: a node used by two consumers gets the gradient of only one of them. Which line is wrong?**
   A. self.grad = 1.0 in backward()
   B. A _backward closure assigns (=) to an input's .grad instead of accumulating (+=)
   C. The topological sort visits leaves first
   D. The forward value is stored as float instead of int
   Answer: B — Each consumer's closure contributes its share to the shared input; with = the last one to run overwrites the others. Seeding self.grad = 1.0 on the output is correct, and a topological order that lists leaves first is exactly what reversed() needs.

**Q2. Why must _backward closures run in REVERSE topological order?**
   A. It is faster
   B. A node may only push gradient to its inputs once its own .grad is complete — i.e. after every node that consumes it has pushed its contribution
   C. Python requires closures to run in reverse creation order
   D. Forward order would compute second derivatives
   Answer: B — A node's _backward multiplies its out.grad into its inputs. If it runs before a later consumer has added its share to out.grad, the inputs receive an incomplete gradient and nothing corrects it afterwards. Reverse topological order guarantees every consumer has run first. Lab 01's topo-order check builds a graph where any other order gives the wrong answer.

**Q3. A training loop calls loss.backward() every step but never resets .grad. What happens?**
   A. Nothing — backward() overwrites old gradients
   B. Each step's gradient is the sum of all previous steps' gradients, so updates grow and point increasingly in stale directions
   C. The graph is rebuilt, so gradients are fresh
   D. Python raises an error
   Answer: B — Parameters are long-lived leaves; their .grad slot accumulates by design, across backward() calls as well as within one. Without a reset, step n applies the sum of n gradients. That is why PyTorch loops call optimizer.zero_grad() — and why gradient accumulation (P1.L2) is just "do not zero for k micro-batches" on purpose.

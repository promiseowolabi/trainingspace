# M1.L1 — Tokenization

_Track M1: The Transformer · ~18 min · trainingspace_

> A language model never sees text. It sees integers from a vocabulary fixed before training began — and the size of that vocabulary is a trade between how long every sequence is and how many parameters the first and last layers cost.
The model is a function of integers. Something has to turn `"The cat sat."` into `[464, 3797, 3332, 13]` before training, and turn the model's integer predictions back into text afterwards. That something is the **tokenizer**, and it is trained once, separately, and then frozen: every embedding row the model learns is tied to a token id.

## Three ways to cut text

| unit | vocabulary | sequence length | problem |
|---|---|---|---|
| characters / bytes | 256 | longest — one per byte | every sequence is 3–4× longer than it needs to be, and attention cost grows with length |
| words | hundreds of thousands | shortest | unseen words, typos, other languages and code have no id |
| **subwords (BPE)** | 30k–250k | in between | none fatal — the standard choice |

**Byte-level BPE** gets the best of both. Start from the 256 byte values, so any string in any language — or any binary garbage — can be encoded. Then repeatedly find the most frequent adjacent pair of tokens in the training corpus and add it to the vocabulary as a new token. After tens of thousands of merges, common words are single tokens, rare words are a few pieces, and nothing is ever unknown.

---

```python
ids = list(text.encode("utf-8"))           # 256 base tokens: the bytes
merges = {}
for new_id in range(256, vocab_size):
    stats = get_stats(ids)                  # count adjacent pairs
    pair = max(stats, key=stats.get)        # most frequent pair
    ids = merge(ids, pair, new_id)          # replace it everywhere
    merges[pair] = new_id                   # the merges ARE the tokenizer
```

## What the merges buy

Training lab 04's tokenizer on its own 3,440-byte corpus and encoding that corpus, on the reference laptop:

| vocabulary | merges | bytes per token |
|---|---|---|
| 256 | 0 | 1.00 |
| 300 | 44 | 1.71 |
| 400 | 144 | 2.87 |
| 512 | 256 | 4.57 |
| 1,024 | 768 | 3,440 — the whole text is one token |

The last row is a warning, not a result: the corpus is one paragraph repeated four times, and with enough merges the tokenizer memorises it. Real tokenizers are trained on gigabytes of diverse text so that the merges capture *common* structure. On English prose, production tokenizers average roughly four bytes per token.

## The vocabulary-size trade

A larger vocabulary means **shorter sequences** — fewer tokens per document, so fewer FLOPs per document (P1.L4) and more text in a fixed context window. It costs **parameters** at both ends of the model: the input embedding is a `(V, C)` matrix and the output layer another `(C, V)` unless they are tied (M1.L5). It also makes each output softmax wider, and gives rare tokens fewer training examples each.

---

> **[vendor snapshot — verified 2026-10]** Vocabulary sizes in practice
>
> GPT-2 used a byte-level BPE vocabulary of **50,257** tokens (50,000 merges, 256 bytes, one end-of-text token). Meta's Llama 3 moved to a **128,256**-token vocabulary, and reported that it encodes language "much more efficiently", yielding up to 15% fewer tokens than Llama 2's 32,000-token vocabulary. At Llama 3 8B's width of 4,096 the input embedding is 128,256 × 4,096 ≈ **525 million** parameters, and the separate output layer the same again — about 13% of the model together.
>
> Sources: https://cdn.openai.com/better-language-models/language_models_are_unsupervised_multitask_learners.pdf · https://ai.meta.com/blog/meta-llama-3/

---

> **[segfault]** - **Arithmetic and spelling.** If "1234" is one token and "1235" is two, the model sees numbers as unrelated symbols; counting the letters of a word it only ever saw as one token is hard for the same reason.
> - **Languages pay different prices.** A tokenizer trained mostly on English cuts other scripts into more tokens per character, so the same sentence costs more compute, fills the context sooner, and — through a paid API — costs more.
> - **Leading spaces.** " cat" and "cat" are different tokens in GPT-2-style vocabularies. Prompt code that strips or adds a space changes the ids the model sees.

**Q1. A team proposes growing their tokenizer's vocabulary from 32k to 256k "for free compression". Which cost are they leaving out?**
   A. None — a larger vocabulary is strictly better
   B. The embedding and output matrices grow with V: at width 4,096, 256k tokens is about 1 billion parameters per matrix, plus a wider softmax and fewer training examples per rare token
   C. Byte-level BPE cannot exceed 65,536 tokens
   D. Sequences get longer
   Answer: B — Compression is real — sequences shrink — but every extra token adds a row to the input embedding and a column to the output layer: 256,000 × 4,096 ≈ 1.05 B parameters each. For a small model that can be most of its parameters. Vocabulary size is a trade, not a free lunch.

**Q2. Why do modern tokenizers start from bytes rather than from characters or words?**
   A. Bytes compress better
   B. With all 256 byte values in the base vocabulary, every possible input — any language, emoji, code, even invalid UTF-8 — can be encoded; there is no unknown token
   C. Models can only read numbers below 256
   D. Bytes make attention cheaper
   Answer: B — A word or character vocabulary always meets inputs it has no id for. Starting from bytes guarantees coverage; the merges then recover efficiency on common text. Coverage is the property; compression comes from the merges.

**Q3. You retrain your tokenizer on a better corpus halfway through a project and load the new tokenizer with your existing pretrained checkpoint. What happens?**
   A. The model improves because the tokenizer is better
   B. The model breaks: its embedding rows were learned for the old ids, and the same id now means a different string — the tokenizer and the weights are one artefact
   C. Nothing — ids are assigned alphabetically
   D. Only rare words are affected
   Answer: B — Token id 3797 indexes row 3797 of the embedding matrix, which was trained to mean whatever 3797 meant in the old vocabulary. Change the merges and every id after the first changed merge refers to a different string. A tokenizer is frozen for the life of the model it was trained with.

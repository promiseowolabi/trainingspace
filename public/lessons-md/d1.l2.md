# D1.L2 — Data Parallelism

_Track D1: Distributed Training · ~19 min · trainingspace_

> Give every GPU a full copy of the model and a different slice of the batch, average the gradients, take the same step everywhere. It is the simplest way to use N devices, the maths is exactly single-device training — and it does nothing at all for memory.
## The algorithm

N ranks, each with a full replica of the model:

1. **Broadcast** the initial weights from rank 0, so every replica starts identical.
2. Each step, split the global batch into N shards; rank r runs forward and backward on shard r.
3. **All-reduce** the gradients and divide by N: every rank now holds the average gradient over the whole batch.
4. Every rank applies the same optimiser step to the same weights with the same gradient — so the replicas stay identical without ever exchanging weights again.

Because the mean of per-shard mean gradients equals the full-batch mean gradient, this is **exactly** single-device training with batch N × B. Lab 10 checks it: two processes on 8 examples each must reproduce one process on 16 to within 10⁻⁶.

_fig 1 — one data-parallel step on 2 ranks_

Components: global batch (16 examples) · rank 0 (fwd + bwd, rows 0–7) · rank 1 (fwd + bwd, rows 8–15) · all-reduce / N (mean gradient) · same step (rank 0) · same step (rank 1)

Steps:
1. The global batch is split by rows. Each rank holds the complete model, so no activations ever cross between ranks.
2. Each rank computes the gradient of its own shard's loss. The two gradients differ — they saw different data.
3. An all-reduce sums the gradients and each rank divides by N. Both now hold the gradient one device would have computed on all 16 examples.
4. Identical weights plus identical gradients give identical updates: the replicas stay in lock-step without ever sending weights.

## What it costs

**Communication.** One all-reduce of every gradient, every step: for N parameters in bf16, 2·N bytes of gradient and about 2 × that sent per rank (D1.L1). A 7B model: 14 GB of gradients, **about 28 GB sent per rank per step**. On a 50 GB/s inter-server link that is 0.56 s. A step processing 32,768 tokens per GPU costs 6 × 7 × 10⁹ × 32,768 ≈ 1.4 × 10¹⁵ FLOPs — about 3.5 s on an H100 at 40% MFU. Done naively after the backward pass, communication adds 16% to every step.

**Overlap** hides it. Gradients for the last layers are ready first, so DDP all-reduces each ~25 MB bucket the moment its gradients are complete, while the backward pass continues into earlier layers. Lab 10 builds the buckets; real DDP also fires them from backward hooks. Well-overlapped data parallelism scales close to linearly — until the batch gets too large.

**Memory: nothing saved.** Every rank holds the full 16 bytes per parameter plus activations for its shard. A 7B model needs 112 GB of training state per GPU (T0.L4), more than an 80 GB H100 has — so plain data parallelism cannot train it at all. D1.L3 fixes that by sharding.

- **14 GB** — 7B gradients, bf16 (7 × 10⁹ × 2 bytes, all-reduced every step)
- **~28 GB** — sent per rank (2(N − 1)/N × 14 GB for large N)
- **0.56 s** — at 50 GB/s (400 Gb/s per GPU — a typical inter-server link)
- **10⁻⁶** — lab 10 agreement (2 processes × 8 examples vs 1 process × 16, after 5 SGD steps)

## The batch-size ceiling

Data parallelism scales by making the global batch bigger: N ranks × B per rank × accumulation steps (P1.L2). That works only up to a point. Beyond a model- and data-dependent **critical batch size**, doubling the batch no longer halves the number of steps needed — each step's gradient is already a good estimate of the true gradient, and averaging more examples adds little. Past that point extra ranks burn compute without speeding up training. This is one reason large runs combine data parallelism with the model-splitting schemes of D1.L4 and D1.L5 rather than adding replicas forever.

**Q1. A team moves a run from 1 GPU with batch 32 to 8 GPUs with 32 per GPU and changes nothing else. What changed about the training maths?**
   A. Nothing — data parallelism is invisible
   B. The global batch is now 256, so each step averages 8× more examples; the learning rate and schedule tuned for batch 32 may no longer be right, and the run takes 8× fewer steps per epoch
   C. Each GPU now trains a different model
   D. The gradients are now 8× larger
   Answer: B — Averaging over ranks makes the effective batch N × B. Gradients are averaged, not summed, so they are not 8× larger, but the step count per epoch and the noise per step change, and learning-rate recipes are tied to the batch size. Data parallelism is exact for the batch it computes, which is not the batch you had before.

**Q2. Why do data-parallel replicas never need to exchange weights after the first broadcast?**
   A. They do — weights are all-reduced every step
   B. Identical starting weights, an identical averaged gradient and an identical deterministic optimiser give identical new weights on every rank
   C. Only rank 0 updates its weights
   D. Weights are stored on a parameter server
   Answer: B — The update is a deterministic function of weights, gradient and optimiser state, all of which are equal across ranks after the all-reduce. That is why the initial broadcast matters so much: if replicas start different, they stay different.

**Q3. Your 7B data-parallel run spends 0.56 s per step in gradient all-reduce and 3.5 s computing. Profiling shows the all-reduce starts only after the whole backward pass ends. What is the main improvement available?**
   A. Use fp32 gradients
   B. Overlap: launch each bucket's all-reduce as soon as its gradients are ready during backward, hiding most of the 0.56 s behind the remaining computation
   C. Reduce the number of ranks
   D. Make buckets as small as possible
   Answer: B — Gradients for later layers are finished early in the backward pass. Bucketed, hook-driven all-reduces overlap communication with the computation still running, which is how DDP keeps scaling efficiency high. Tiny buckets would add latency instead.

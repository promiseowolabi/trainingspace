# F1.L3 — LoRA

_Track F1: Post-Training · ~18 min · trainingspace_

> Fine-tuning every weight of a 7B model needs 112 GB of training state. Freeze the weights and learn a low-rank correction to a few matrices instead, and the trainable part shrinks to a quarter of a percent — with no extra cost at inference once it is merged back in.
## The idea

Full fine-tuning updates a weight matrix W (d_out × d_in) to W + ΔW. LoRA's hypothesis (Hu et al., 2021) is that for adapting a pretrained model, the useful ΔW has **low rank**: it can be written as a product of two thin matrices,

```
ΔW = (α / r) · B · A          A: r × d_in,   B: d_out × r,   r ≪ d
```

So freeze W and train only A and B. The layer computes

```
y = W·x + (α / r) · B·(A·x)
```

through a bottleneck of width r — two thin matmuls that cost a sliver of the base layer.

Two details make it work:

- **B starts at zero.** The adapter is a no-op at step 0, so fine-tuning starts exactly from the pretrained model. A starts random, so that B receives a non-zero gradient on the first step. (Lab 12's `zero-init` and `frozen-base` check both.)
- **α / r scaling.** Dividing by r keeps the adapter's effect roughly independent of rank, so a learning rate tuned at r = 8 still works at r = 16.

## The arithmetic

A 7B-class model with 32 layers of width 4,096, LoRA rank 16 on the q, k, v and output projections:

```
per matrix:  r · (d_in + d_out) = 16 · (4,096 + 4,096) = 131,072
per layer:   4 matrices                                  = 524,288
model:       32 layers                                    = 16.8 M   (0.25% of 6.7 B)
```

Training memory (T0.L4), before activations:

| | full fine-tuning | LoRA r = 16 |
|---|---|---|
| bf16 weights | 13.4 GB | 13.4 GB (frozen) |
| gradients | 13.4 GB | 0.03 GB |
| fp32 master + Adam m, v | 80.4 GB | 0.2 GB |
| **total** | **≈ 107 GB** | **≈ 13.6 GB** |

From "a multi-GPU job" to "one 24 GB card". Activations are unchanged — the forward and backward passes still go through every frozen layer — so long sequences still need activation memory.

**QLoRA** goes one step further: store the frozen base in 4-bit precision (about 3.4 GB for 6.7 B parameters), dequantise each layer on the fly for the matmul, and keep the small adapters in bf16.

---

_fig 1 — a LoRA layer_

Components: x ((…, d_in)) · W · x (frozen, d_out × d_in) · A · x (r × d_in) · B · (Ax) (d_out × r) · + (× α / r) · y ((…, d_out))

Steps:
1. The pretrained weight W computes its usual output. It is frozen: no gradient, no optimiser state, stored in bf16 (or 4-bit for QLoRA).
2. In parallel, A projects x down to r dimensions and B projects it back up — a rank-r path whose cost is r·(d_in + d_out) multiply-adds per token.
3. The adapter's output is scaled by α/r and added. Because B starts at zero, the sum equals W·x on the first step.
4. After training, W + (α/r)·B·A is a single matrix of the original shape: merged, the layer costs exactly what the base layer cost.

---

## Merge or keep separate

After training, `W' = W + (α/r)·B·A` can be computed once and stored — a merged model with **zero** inference overhead (lab 12's `merged`). Or the adapters can be kept separate: one base model in memory, many small adapters (tens of megabytes each) swapped per request or per customer. Both are common.

## What it is good and bad at

LoRA matches full fine-tuning closely for adapting behaviour, format and domain style — most SFT and preference tuning. It is weaker when the task needs substantial new capability or knowledge, where the low-rank constraint bites; applying it to the MLP matrices as well as attention, or raising r, narrows the gap. As always: measure on held-out data.

**Q1. A LoRA adapter is initialised with both A and B equal to zero. What happens in training?**
   A. It trains normally
   B. Nothing ever changes: with B = 0 the gradient to A is zero, and with A = 0 the gradient to B is zero, so both stay at zero forever
   C. It diverges
   D. It learns twice as fast
   Answer: B — ∂y/∂A involves B and ∂y/∂B involves A·x. If both are zero, both gradients are zero. That is why one factor (B) starts at zero — to make the adapter a no-op — and the other (A) starts random so learning can begin.

**Q2. Where does LoRA save memory, and where does it not?**
   A. It saves activation memory only
   B. It removes nearly all gradient and optimiser-state memory (they exist only for A and B) but keeps the frozen weights in memory and does not reduce activations
   C. It shrinks the model weights by r / d
   D. It saves nothing during training, only at inference
   Answer: B — The 12 bytes per parameter of optimiser state and the 2 of gradients apply only to trainable parameters — 0.25% of the model in this lesson's example. The frozen weights still have to be held for the forward pass, and every layer's activations are still stored for the backward pass.

**Q3. A service needs 50 customer-specific fine-tunes of the same 7B model. Why is LoRA attractive beyond training cost?**
   A. Each adapter is a few tens of megabytes, so one copy of the base model can serve all 50 by swapping adapters, instead of storing and loading 50 full 13 GB models
   B. LoRA models are more accurate
   C. Adapters run without the base model
   D. It removes the need for a tokenizer
   Answer: A — r·(d_in + d_out) per adapted matrix is tiny next to the base weights. Keeping adapters separate lets many fine-tunes share one base model in memory; merging is only needed when a single variant must have zero overhead.
